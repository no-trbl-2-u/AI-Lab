The self-improving agent that quietly gets worse

Ye, Li, Pruksachatkun, Zhang & Wu · Salesforce AI Research · 18 Aug 2026 · arXiv:2608.18066

Agents that learn by writing lessons to a memory bank look like they improve — but the improvement is mostly an artifact of running the experiment once, in a conveniently easy-to-hard task order. Run it three times and shuffle the order, and the memory loop adds noise and drops below an agent with no memory at all.

01The problem it exists to solve

You have an agent that keeps notes. After each job it writes down what it learned, and it reads those notes before the next job. Over a few hundred jobs it should get better. The papers say it does.

But how would you know? Everyone reports a single run. An agent doing multi-step work in a messy environment is noisy to begin with, and a note-taking loop is stateful — a lucky success early gets written down, retrieved, and built on; an unlucky one does the same in the other direction. Two runs of the identical setup end up with different notebooks. So the number you publish is one draw from a distribution nobody measured.

There is a second, quieter problem. Benchmarks list easy tasks first, because that is the order people write them in. An agent learning across that stream gets a free curriculum. Real users do not submit their requests easiest-first.

02How it works — where the loop goes wrong

The setup is a loop: do a task, write a lesson, file it, retrieve it next time. The paper's contribution is showing that the thing writing the lessons cannot see the environment — so it writes advice that is sensible in the abstract and impossible here, and the loop then makes that advice more likely over time.

03How much to believe it

Read this before the numbers, not after. This paper is unusually strong on evidence — but not uniformly, and the two halves are not equally solid.

◆
Measured The variance and task-order findings.

3 identical runs × 3 benchmarks (WebArena 812 tasks, VisualWebArena 910, SCUBA 267) × 3 task orders. Ground-truth rewards, not an LLM judge. Standard deviations and best-worst gaps reported per domain. This is the half you can lean on.

▲
Measured, n = 3 Three runs is enough to see noise, not to price an effect.

The authors say so themselves: their own headline gain of +1.5% carries p = 0.23. That cuts both ways — it undercuts the method's claimed gain, and it also means small differences between their conditions are not resolvable.

▲
Qualitative The underspecification diagnosis — including the Haversine story.

Hand-inspection of a subset of memories. Appendix A states plainly that an exhaustive review was infeasible and that other failure patterns likely exist. The keyword-frequency plots are real counts, but the causal story around them is a hypothesis with good illustrations, not a measured mechanism.

●
Scope limit Web browsing, two methods, one backbone model.

GPT-5-mini throughout. No other domain, no other memory technique, and none of the most recent memory-management work. Whether this transfers to a memory over a stable curated corpus — rather than self-written lessons — is untested here.

04The numbers

The single most useful statistic is the best-worst gap: run the same configuration three times, and this is the spread between the luckiest and unluckiest result. It is the range a single-run number could have landed in by chance — so any claimed improvement smaller than this bar is indistinguishable from luck.

The effect being claimed

+1.5% average gain from ReasoningBank on WebArena — with p = 0.23. AWM managed −0.7%. Meanwhile the luck window on a single domain reaches 10.4 points.

What shuffling costs

WebArena drops from 54.8% (no memory) to 49.1% with AWM and 49.8% with ReasoningBank once task order is randomised. Not a lost gain — an actual loss.

The baseline nobody ran

Their plain no-memory agent scores 54.8% — beating both original papers' memory-enhanced results (36.3% and 53.9%). The methods were measured against weaker agents than exist now.

What the fix recovers

Feeding the memory writer the rubric, the environment's error messages, and an explicit "don't suggest APIs" recovers 31% of the damage. 69% is unexplained, and the authors decline to guess.

05The one thing to remember

“Without proper validation mechanisms, agent memories are merely unverified hypotheses rather than true lessons learned.”

Everything we have written about memory is about where things go — partitions, retrieval, decay, promotion. None of it asks whether the thing written down is true. A memory system with no correctness gate is not a filter on experience; it is an amplifier, and the thing it amplifies loudest is whatever got written early.

06What we take from it

Take

  • Three runs, not two. Our measurement gap (G4) currently closes on a same-day double run. Two runs give a gap; they do not give a spread, and they cannot see order as a confound.
  • Shuffle the inputs. One line of code, and it is the cheapest stress test in the paper. Any fixed prompt set we build has an implicit order.
  • Never report a single-run number for a skill's behaviour without saying it is single-run.
  • Tell the writer what it cannot do. Their most effective single intervention was a negative list — "strictly avoid API solutions, external sites, asking a human" — pasted into the memory prompt.

Leave

  • The 9× evaluation budget, unconditionally. Three runs × three orders is right for something that accretes state. It is overkill for a skill that starts fresh each time.
  • The specific numbers as transferable. These are web-browsing pass rates on GPT-5-mini. The protocol transfers; 4.4% does not.
  • The underspecification diagnosis as settled. It explains 31% of the effect and rests on a partial hand-inspection. Treat it as the leading hypothesis, not the cause.

Where it argues with the pool

Against note 09 §5 — "keep the wrong stuff in." Manus says leave failures visible so the model stops repeating them. That is advice about the context window. This paper's failure is in the persistent store: ReasoningBank writes lessons from failed runs too, and they compound instead of inoculating. The boundary was never stated because Manus had no memory bank. Keep errors in the window; gate what reaches the bank.
Against note 15 — outcome-weighted retrieval. Springdrift demotes memories that lead to failures. The Haversine strategy occasionally succeeds, so its utility score stays respectable while the strategy is wrong. Outcome-weighting filters usefulness, not correctness.
Against note 14 — the promotion ladder. Note 14's cheapest promotion trigger is access-driven: promote what gets retrieved often. That is exactly the curve the paper plots for a contaminated memory — contagion is retrieval frequency. A frequency counter promotes the wrong lesson fastest.
