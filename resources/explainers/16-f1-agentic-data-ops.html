F1's Agentic Data Ops

AWS Machine Learning Blog · Formula 1 + AWS engineers · 2026 · read the source
How F1's MarTech team used Bedrock AgentCore agents to speed up data-source onboarding

F1 cut new-data-source onboarding from 6–8 weeks to ~40 minutes of code generation by having an agent draft the pipeline as pull requests — and every PR still needs a human to approve it before anything ships.

01The problem it exists to solve

Every new MarTech data source meant hand-writing schema mappings, pipelines, quality checks, and GDPR tags from scratch — and providers changed schemas without notice, often mid race-weekend.

Manual onboarding

  • 6–8 weeks of engineering per source
  • 18-month backlog for 12 sources
  • Schema drift breaks pipelines with no warning
  • Debugging means tracing S3, Redshift, Airflow, DBT by hand

Agent-drafted onboarding

  • ~40 min of code generation + review hours
  • Agent opens PRs; engineer still approves each one
  • Drift agent proposes a fix PR, explains the change
  • Context graph explains failures in business terms
AI proposes, humans decide.

That line is the whole safety model. Nothing here claims the agent replaces engineering judgment — only that it drafts the boilerplate an engineer used to write by hand.

02How it works

One agent, not a swarm, with modular "skill" definitions for schema mapping, data quality, governance, and PII classification. It can open a pull request. It cannot merge one.

The idea most worth stealing: the enforcement isn't a hook or a prompt rule — it's structural. The agent's credentials simply don't include a merge permission. It cannot be argued, prompted, or drifted out of a capability it was never issued.

05The one thing to remember

The article is titled around "agentic AI," but only two of the five workstreams it describes actually involve an agent making a decision.

Data source onboarding — agent drafts config & pipeline PRsAgentic
Schema evolution detection — agent proposes fix PRsAgentic
Unified data access — declarative config, not agent-drivenNot agentic
Observability / RCA — reads & explains, doesn't actRead-only
Identity resolution — plain algorithm profiling & tuningNot agentic

That gap between the framing and the content is itself the most useful thing to take from this piece — a reminder to check, in any "agentic AI" writeup, which parts are actually agents deciding something.

06What we take from it

Take these

  • Structural no-merge permission. The cheapest enforcement tier — a capability the agent never holds, not a rule it might drift past.
  • PR-as-approval-gate. Every generated change surfaces as one reviewable diff, however many files the agent touched.
  • Context-graph-augmented RCA. Pairing raw failure logs with a hand-authored topology graph turns symptoms into explanations.

Leave these

  • The headline percentages. Unaudited, self-reported, and missing the one number (rework rate) that would test them.
  • "Agentic AI platform" as a description of all five workstreams. Three of five aren't agentic at all.
Where this lands in the pool: it's a real production data point on two existing tensions rather than new mechanism. It lands on 08's side of the 07-vs-08 multi-agent question — F1 chose one agent with modular skills, not an orchestrator with workers, for a case that could plausibly have gone either way. And it confirms 11's enforcement-boundary thesis from outside the abstract: the entire safety story here is infra-tier (scoped tokens, VPC, structural no-merge), not a hook or a prose rule asking the agent to behave.
